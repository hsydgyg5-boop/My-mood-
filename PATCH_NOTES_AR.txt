إصلاح توافق تشغيل مزاجي على Railway

تم تعديل ما يلي دون حذف قاعدة البيانات أو مجلد USERS:
1) عند فتح موقع ثابت، تكون الصفحة الرئيسية index.html / index.htm / home.html؛ ولا يُستخدم main.py أو app.py كصفحة رئيسية بسبب startup_file قديم.
2) يمنع رابط الموقع الثابت من نشر ملفات Python وسجلات وإعدادات التشغيل كنص عام.
3) تحسين كشف نوع المشروع: ملفات JavaScript الخاصة بواجهة HTML لا تجعل الموقع Node.js تلقائياً، بينما تستمر مشاريع Node التي لها اعتماديات/خادم فعلي في التعرف عليها.
4) تصحيح ملف بدء التشغيل حسب نوع المشروع، دون تغيير أنواع الخوادم الحالية الصحيحة عند إقلاع لوحة الإدارة.
5) إزالة فرض نوع Node.js لمجرد رفع ملف JavaScript منفرد؛ يعاد تحديد النوع من مجموعة ملفات المشروع بعد الرفع.

تشغيل لوحة مزاجي على Railway:
- Procfile و railway.toml يحددان الأمر: gunicorn app:app --bind 0.0.0.0:$PORT --workers 1 --threads 4 --timeout 120
- يتم تثبيت المكتبات من requirements.txt.
- لدوام بيانات المستخدمين، أبقِ Railway Volume على /data ولا تستخدم Wipe Volume.

الاختبارات المنفذة محلياً: فحص صياغة Python، واختبارات كشف أنواع المشاريع (Static / Python / Node.js)، واختبار مسار الصفحة الرئيسية بحيث يعرض HTML ولا يعرض مصدر .py، وفحص سلامة ZIP.
لم يتم إجراء نشر على حساب Railway الحقيقي من هذه البيئة.


تحديثات واجهة وخادم إضافية:
6) زر رفع تلقائي يطلب اسم السيرفر قبل الرفع.
7) إضافة حد ملفات للمستخدم افتراضيه 10، ويمكن تعديله من لوحة الإدارة؛ يُطبق على رفع الملفات وإنشاء الملفات وفك ضغط ZIP.
8) إصلاح API إدارة سيرفرات المستخدمين الذي كانت لوحة الإدارة تستدعيه دون وجود مسار له، وإضافة فتح/تشغيل/إيقاف/إعادة تشغيل/حذف/تنزيل ملفات السيرفرات للمسؤول.
9) محرر الملفات يحتوي حفظ ورجوع وتنبيه للتعديلات غير المحفوظة، ولا يسمح بتحرير الملفات الثنائية كنص.
10) إخفاء تنبيه Railway Volume من واجهة المستخدم فقط؛ بقي تشخيص التخزين في السجلات والواجهة البرمجية. يجب ربط Volume فعليًا في Railway ولا يمكن إجراء ذلك من ملف ZIP.
11) تحسين تثبيت اعتماديات Python مع إنشاء venv وتحديث pip عند الحاجة وإعادة المحاولة مرة واحدة، وكتابة سبب الفشل في السجل ومنع التشغيل التلقائي بعد فشل التثبيت.

مراجعة تدقيق محلية إضافية (2026-10-20):
12) إصلاح عطل مباشر في تجهيز Python بسبب استعمال pathlib.Path دون استيراده، والتأكد من إنشاء بيئة .venv وتشغيل مشروع Python تجريبي يعتمد على المكتبات القياسية.
13) جعل تجهيز Python يعيد مطابقة requirements.txt في كل عملية تجهيز حتى يستطيع pip إصلاح الحزم المفقودة حتى إن لم يتغير الملف، ثم يشغّل pip check لاكتشاف الاعتماديات المفقودة أو المتعارضة. عند الفشل، يُمنع التشغيل التلقائي ويُكتب تشخيص في السجل.
14) تحسين حفظ db.json باستخدام كتابة ذرية واسم ملف مؤقت فريد، مع إعادة المحاولة إذا حصل تعارض أثناء تسلسل البيانات المتزامن.
15) تدقيق عدّ الملفات: أصبحت ملفات النظام مستثناة فقط عندما تكون في جذر المشروع، أما الملف الذي يحمل اسمًا مشابهًا داخل مجلد فرعي للمستخدم فيُحتسب ويظهر. تُرفض أسماء السجلات الداخلية عند الرفع أو التحرير أو الاستبدال أو إعادة التسمية أو الحذف، ويُرفض ZIP الذي يحاول الكتابة لمسارات خارجية أو استخدام روابط رمزية أو استبدال أسماء النظام أو تكرار المسارات.
16) إضافة حد لحجم الملف الذي يُفتح في محرر المتصفح (5 MiB) لتجنّب تحميل ملفات كبيرة جدًا في الذاكرة؛ يمكن تنزيل الملفات الأكبر وتعديلها ثم رفعها مجددًا.
17) تحديث معالجة مدخلات إدارة المستخدم وحد الملفات بحيث تُفحص القيم قبل تغيير سجل المستخدم، وتظل قيمة حد الملفات الافتراضية للمستخدم الجديد 10.
18) زر الملفات يظهر باسم «فتح الملف»، مع حفظ وتراجع وتنبيه للتعديلات غير المحفوظة.
19) إزالة التنبيه المرئي عن Railway Volume مع الإبقاء على معلومات التشخيص في سجل الخادم وواجهة API؛ الإزالة لا تقوم بربط Volume فعليًا.

الاختبارات المحلية الإضافية:
- Python compile: نجح لملفات Python الرئيسية.
- فحص JavaScript المضمّن في index.html وadmin_panel.html وlogin.html باستخدام node --check: نجح.
- اختبار وظائف التطبيق باستخدام Flask stub لأن Flask الحقيقي غير متوفر في بيئة الفحص: تسجيل دخول الإدارة، إنشاء المستخدمين والتحقق من أسماء المسارات، حفظ محرر الملفات، عزل المستخدمين، طلب اسم السيرفر، إنشاء سيرفر تجريبي، وإظهار السيرفر ضمن بيانات الإدارة: نجح.
- اختبارات حدود الملفات وZIP: احتساب ملفات فرعية اسمها يشبه السجلات، رفض الأسماء المحجوزة، ورفض ZIP يحتوي path traversal أو روابط رمزية أو أسماء مكررة: نجحت.
- اختبار بيئة Python حقيقية على الجهاز لملف يعتمد على المكتبات القياسية، ثم إعادة فحص requirements.txt غير فارغ وpip check: نجح.
- فحص قاعدة JSON وقائمة الملفات وسلامة ZIP وفحص أنماط رموز Telegram: نجح.

قيود يجب عدم إخفائها: لم يمكن تثبيت Flask وتشغيل الخادم الحقيقي في بيئة الفحص بسبب عدم توفر اتصال الحزم، ولم يتم نشر النسخة على Railway الحقيقي. لذلك تُعد نتائج الفحص المحلي إيجابية، لكن الاختبار النهائي بعد النشر مطلوب. يجب ربط Railway Volume فعليًا على /data لضمان التخزين الدائم.
